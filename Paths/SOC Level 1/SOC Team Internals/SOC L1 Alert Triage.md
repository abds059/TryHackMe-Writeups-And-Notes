## Task 2 - Events and Alerts

On a SOC dashboard we see a lot of alerts coming and disappearing after some work and time. A lot of alerts can be seen like "Email marked as phishing" or "RDP Bruteforce detected". What are exactly these alerts and what is an alert at its basic definition ? This is exactly what we will uncover in this section.

### From Events To Alerts

For a SIEM to display an alert a process (event) must occur. This may be any activity on a monitored endpoint. Then that activity will be recorded as a log by the target system and then shipped to an EDR or SIEM that may run it through a set of rules to form an alert.

An **Alert** is  a notification that is generated by a security solution whenever a specific set of events occur. This saves a lot of manual review time for SOC Analysts (time that would have been required for manual log review) and allows them to see only events that are of specific importance. 

### Alert Management Platforms

| Solution | Examples | Description |
| :--- | :--- | :--- |
| **SIEM** | Splunk ES, Elastic | SIEMs have solid alert management capabilities and are a perfect choice for most SOC teams. |
| **EDR or NDR** | MS Defender, CrowdStrike | While EDR and NDR provide their own alert dashboards, it is preferred to use SIEM or SOAR. |
| **SOAR** | Splunk SOAR, Cortex SOAR | Bigger SOC teams can use SOAR to aggregate and centralise alerts from multiple solutions. |
| **ITSM** | Jira, TheHive | Some teams may have a custom ticket management (ITSM) setup using a dedicated solution. |

### L1 Role In Alert Triage

Now we have understood what an alert is so we can now move onto understanding what we have to do when we encounter an alert as an L1 analyst and what role others play in a SOC team:

- **SOC L1 analysts:** Review the alerts, distinguish bad from good, and notify L2 analysts in case of a real threat
- **SOC L2 analysts:** Receive the alerts escalated by L1 analysts and perform deeper analysis and remediation
- **SOC engineers:** Ensure the alerts contain enough information required for efficient alert triage
- **SOC manager:** Track speed and quality of alert triage to ensure that real attacks won't be missed

## Task 3 - Alert Properties

We now understand what is an alert so we can move forward to understanding teh concepts associalted wit it. While the content of an alert may differ based on the SIEM or security solution bt the core properties are same. 

![Contents of an Alert](../../../IMAGES/Paths/SOC%20Level%201/SOC%20Team%20Internals/SOC%20L1%20Alert%20Triage/Contents%20of%20an%20alert.png)

| № | Property | Description | Examples |
| :---: | :--- | :--- | :--- |
| **1** | **Alert Time** | Shows alert creation time. The alert usually triggers a few minutes after the actual event. | `Alert Time`: March 21, 15:35<br>`Event Time`: March 21, 15:32 |
| **2** | **Alert Name** | Provides a summary of what happened, based on the detection rule's name. | • Unusual Login Location<br>• Email Marked as Phishing<br>• Windows RDP Bruteforce<br>• Potential Data Exfiltration |
| **3** | **Alert Severity** | Defines the urgency of the alert. Initially set by detection engineers but can be altered by analysts if needed. | 🟢 Low / Informational<br>🟡 Medium / Moderate<br>🟠 High / Severe<br>🔴 Critical / Urgent |
| **4** | **Alert Status** | Informs if somebody is working on the alert or if the triage is done. | 🆕 New / Unassigned<br>🔄 In Progress / Pending<br>✅ Closed / Resolved<br>*(And often other custom statuses)* |
| **5** | **Alert Verdict** | Also called alert classification. Explains if the alert is a real threat or noise. | 🔴 True Positive / Real Threat<br>🟢 False Positive / No Threat<br>*(And often other custom verdicts)* |
| **6** | **Alert Assignee** | Shows the analyst assigned (or who assigned themselves) to review the alert. | • Assignee is sometimes called the **Alert Owner**<br>• Assignee takes responsibility for their alerts |
| **7** | **Alert Description** | Explains what the alert is about, usually in three sections on the right. | • The logic of the alert generating rule<br>• Why this activity can indicate an attack<br>• *(Optionally)* How to triage this alert |
| **8** | **Alert Fields** | Provides SOC analysts' comments and values on which the alert was triggered. | • Affected Hostname<br>• Entered Commandline<br>• *(And many more, depending on the alert)* |

## Task 4 - Alert Prioritisation

### Picking The Right Alert

Since we may encounter many alerts at the same time so picking the alerts in a specific order is necessary to minimize attacks. The most generic approach is listed below:

- **Filter the alerts:** 

    First we need to filter out the alerts that are already being investigated by someone else or have been reviewed. This ensured that we take on only those alerts that need to be reviewed.

- **Sort by severity:**

    Start of with critical level alerts, then high severity ones and gradually the low priority ones to ensure real major threats are handles first as they can cause more impact.

- **Sort by time:**

    Sorting by time is also necessary as older alerts should be investigated first as the attacker may already have penetrated deep into the system. In comparision the new alert may only be telling about any reconnaisance attempts (attacker is trying to map out the attack surface and looking for potential weak services).

## Task 5 - Alert Triage

After alert prioritisation, we need to take an action on that alert or in other terms we have to review the alert we have picked. This involves a series of steps that are illustrated below:

![flowchart](../../../IMAGES/Paths/SOC%20Level%201/SOC%20Team%20Internals/SOC%20L1%20Alert%20Triage/Alert%20Review%20Steps.png)

### Initial Actions

Here we take the ownership of that alert, by assigning ourself to that alert assignee and changing the alert status to **In Progress**. 

### Investigation

This is the most complex step that requires applying one's technical knwoledge to the test. The main purpose here is to determine whether the alert is true or false. For the purpose many teams also have a **Playbook** that contains instructions as to how to proceed with a specifc category of alerts. If any Workbook or Playbook is not available then a safe procedure is:

- Understand who is under threat, like the affected user, hostname, cloud, network, or website
- Note the action described in the alert, like whether it was a suspicious login, malware, or phishing
- Review surrounding events, looking for suspicious actions shortly after or before the alert
- Use threat intelligence platforms or other available resources to verify your thoughts

### Final Actions

The final actions involve stating the verdict whether the alert is **True Positive** or **False Positive**. Also, a detailed comment explaining analysis steps and veridct reasoning should also be added. After all this we can change the alert's status to **Closed**.
